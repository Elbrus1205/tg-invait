ПОЛНЫЙ ПРОМПТ ДЛЯ СОЗДАНИЯ TELEGRAM-ПАНЕЛИ НА VDS

Создай полноценную production-ready веб-платформу для управления Telegram-аккаунтами на собственном VDS-сервере.

Проект должен напоминать по логике панели управления сервисы уровня TG Ninja, но не копировать их дизайн или закрытые механизмы. Платформа должна работать только с Telegram-аккаунтами, которыми пользователь владеет или имеет право управлять, и не должна обходить ограничения, антиспам, FloodWait или другие защитные механизмы Telegram.

Главная идея:
VDS
↓
Web Panel
↓
Backend API
↓
PostgreSQL + Redis/BullMQ
↓
Telegram Workers
↓
Telegram Accounts
↓
Individual Proxy

Администратор должен иметь возможность:
- добавлять Telegram-аккаунты;
- импортировать собственные TData;
- назначать аккаунтам прокси;
- управлять прокси через общий Proxy Manager;
- читать разрешённые переписки аккаунтов;
- отправлять сообщения из панели;
- видеть логи;
- видеть состояние аккаунтов;
- создавать задачи;
- загружать Excel/CSV со списками пользователей для разрешённых приглашений;
- распределять задачи между аккаунтами;
- видеть статистику работы каждого аккаунта;
- управлять всем через удобную адаптивную веб-панель.

==================================================
2. АРХИТЕКТУРА
==================================================

Разделить приложение минимум на:

1. frontend
2. backend
3. telegram-worker
4. postgres
5. redis
6. nginx

Telegram workers должны работать отдельно от HTTP backend.

HTTP backend не должен выполнять долгие Telegram-задачи внутри HTTP request.

Backend:
- принимает команды;
- валидирует данные;
- записывает задачи в базу;
- отправляет их в Redis/BullMQ.

Worker:
- получает задачи;
- работает с Telegram;
- возвращает результаты;
- пишет логи;
- обновляет состояние.

Архитектура должна позволять подключить несколько VDS с workers в будущем.

==================================================
7. TDATA IMPORT
==================================================

Создать страницу:

Telegram → Import TData

Поддержать загрузку:

- ZIP;
- папки/архива с TData, если frontend/runtime позволяет.

Логика:

1. принять файл;
2. проверить формат;
3. распаковать во временную директорию;
4. проверить структуру Telegram Desktop TData;
5. попытаться определить аккаунт;
6. если технически возможно, конвертировать TData в Telegram session, совместимую с используемой библиотекой;
7. проверить авторизацию;
8. получить:
   - Telegram ID;
   - username;
   - phone;
   - first_name;
   - last_name;
   - avatar;
9. сохранить новую Telegram session;
10. удалить временные файлы;
11. удалить исходный ZIP после успешной обработки.

Важно:

- TData не должна сохраняться в открытом виде;
- не выводить содержимое TData в логах;
- не делать публичных ссылок на TData;
- временная директория не должна быть доступна через Nginx;
- session хранить зашифрованно;
- при ошибке показывать понятное сообщение.

Поддержать массовый импорт нескольких TData.

24. TELEGRAM LIMITS ДЛЯ INVITATIONS
==================================================

Строго обрабатывать:

- FLOOD_WAIT
- PEER_FLOOD
- USER_PRIVACY_RESTRICTED
- USER_NOT_MUTUAL_CONTACT
- USER_ALREADY_PARTICIPANT
- USERNAME_NOT_OCCUPIED
- CHAT_ADMIN_REQUIRED
- CHANNEL_PRIVATE
- USER_CHANNELS_TOO_MUCH
- CHAT_WRITE_FORBIDDEN
- RPC errors

При FLOOD_WAIT:

1. получить Telegram wait time;
2. сохранить wait until;
3. поставить аккаунт/задачу на паузу в рамках этого аккаунта;
4. продолжить только после разрешённого Telegram времени.

Не переключать автоматически на другой аккаунт специально для обхода ограничения.

==================================================

- защищать от двойного запуска session.

==================================================
TELEGRAM ERROR HANDLING
==================================================

При получении Telegram ограничения или ошибки система должна корректно остановить соответствующее действие.

Обрабатывать:

- FLOOD_WAIT;
- PEER_FLOOD;
- USER_PRIVACY_RESTRICTED;
- USER_NOT_MUTUAL_CONTACT;
- USER_ALREADY_PARTICIPANT;
- USERNAME_NOT_OCCUPIED;
- CHAT_ADMIN_REQUIRED;
- CHANNEL_PRIVATE;
- USER_CHANNELS_TOO_MUCH;
- CHAT_WRITE_FORBIDDEN;
- RPC errors.

При FLOOD_WAIT:

1. получить официальное время ожидания Telegram;
2. сохранить FloodWait Until;
3. немедленно остановить Invitation действия данного аккаунта;
4. показать аккаунт как FloodWait;
5. не выполнять новые Invitation действия до окончания указанного Telegram времени;
6. после окончания времени не запускать действия автоматически, если задача или аккаунт были вручную остановлены;
7. записать событие в Account Activity History;
8. отправить уведомление администратору.

Не использовать другой аккаунт автоматически для обхода ограничения.

При PEER_FLOOD или других ограничениях:

- остановить соответствующее действие;
- сохранить ошибку;
- показать статус;
- не выполнять автоматический обход ограничения;
- не выполнять автоматическую смену аккаунта с целью продолжения запрещённой активности.
